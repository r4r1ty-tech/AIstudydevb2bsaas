# План: бот на онлайн-лекции SSAU

Личный инструмент на ~5 человек одной группы. Не публичный SaaS.

## Зачем

Не сидеть на онлайн-парах, но:

1. **Посещаемость** — в BBB в списке участников видно ФИО, как в журнале. Камеру не просят, микрофон не нужен.
2. **Пейджер** — на паре лёгкий споттинг вейквордов по **одному** аудиопотоку: фамилия, «тест», «контрольная», «мудл». Это не расшифровка лекции. Полный текст — **после** пары, по API.
3. **Архив** — часть пар не пишется универом. Раз уже внутри комнаты, один раз пишем звук на диск VDS.

За 15 минут до пары в личку: предмет, препод, время, кнопки Да / Нет. Молчание = зайти. Нет = сегодня пропуск.

## Что сознательно не делаем

- Прокси и антибот-обход. Ходим с IP VDS, как есть.
- Один бинарник «всё в одном»: ТГ + парсер + панель + BBB в одном процессе. Это микросервисы.
- Ответы в чат BBB, включение камеры/микрофона.
- Пересылка уведомлений ЛК: там рассылки без пользы, не берём.
- Отдельная копия записи на каждого кента, если это одна и та же лекция.
- Полный Whisper/большая модель **во время** пары. На лекции только Chrome + запись + крошечный keyword-споттер.

## Решения с гриля

| Тема | Решение |
| --- | --- |
| Кто | Я + кенты, одна группа, потолок ~5 человек |
| Площадка | `bbb.ssau.ru` (Greenlight), заход **гостем**, поле имени как скажет человек боту |
| Расписание | Из **ЛК** (`lk.ssau.ru`, `timetable/get-timetable`) по сохранённому аккаунту: подгруппы, пары ИОТ, онлайн по неделям. Нет аккаунта или ЛК лежит — публичный `https://ssau.ru/rasp?groupId=…` |
| Ссылка BBB | Приходит из ЛК вместе с парой (`conference.url`). Ручная ссылка пары важнее; без ЛК — как раньше: спросить URL `bbb.ssau.ru/b/…` и запомнить |
| Подгруппа | Задаётся руками при первом входе в веб-приложение (вместе с ФИО для BBB). ЛК говорит, у какой подгруппы пара, но не в какой подгруппе студент |
| Moodle | `do.ssau.ru/moodle`: вход по форме, все курсы студента (и прошлые — у них бывают открытые тесты), задания и тесты со сроком, статусом и «что сделать». Без срока — отдельный спокойный блок, не горит |
| Пароли | ЛК/Moodle хранятся зашифрованными (AES-GCM, ключ вне базы), чтобы синк ходил сам; «Отключить» стирает |
| Фокус | Сейчас — **веб-приложение** (пользуется админ). Telegram-бот работает как есть, новое в нём пока не развиваем |
| Telegram | Один бот. Отвечает **только** айдишникам из вайтлиста. Чужим — тишина |
| Админ-панель | Mini App только у админа из `ADMIN_TELEGRAM_ID` (дефолт `700000000`): вкладки + пульт + логи. Админ имеет доступ даже без вайтлиста. HTTPS без своего домена (туннель) |
| Парсер-ключи | Позже: ключи от кентов (Fish Studio и ещё что дадут). Слот в конфиге есть, в v1 не блокер |
| Прокси | Не используем. Все заходы с одного IP VDS |
| Аудио в BBB | Всегда «только слушать». Лобби >2 мин → алерт «не пустили» |
| Выход | Случайные 0–5 минут **до** конца слота из расписания (преподы сами часто режут раньше) |
| Запись | Папка на VDS. Одна лекция = один файл, даже если зашло пятеро |
| Вейкворды | Живые, по одному потоку. Короткие слова, не полный транскрипт. Расшифровка лекции — API после записи |
| Железо | VDS **4 CPU / 4 ГБ RAM + 4 ГБ swap**. Один Chrome: 1 умная вкладка + 4 в списке |
| Рефреш расписания | Фон: **07:00, 15:00, 19:00, 22:00** (локальное время Самары). Изменилось — перезаписать |

Группа-якорь: `6301-090301D`, `groupId=531023229`.

## Вайтлист Telegram

Бот не онбордит с улицы. Нет id в списке — нет ответа (и нет Mini App).

| Роль | Telegram user id |
| --- | --- |
| Админ (я), Mini App | `700000000` |
| Кент | `600000001` |
| Кент | `600000002` |
| Кент | `600000003` |
| Кент | `600000004` |

Итого 5 человек, как в потолке. Сиды в конфиге, живое состояние (вкл/выкл, ФИО, вейкворды) — sqlite, крутится из Mini App.

## Админский Telegram Mini App

Пульт, не картинка. Открывается **только** у админа (`ADMIN_TELEGRAM_ID`, дефолт `700000000`). Кентам — обычные лички, без `web_app`. Вайтлист и админ — разные вещи: админ в него не обязан входить.

Глобальную Menu Button в BotFather не ставим (она у всех). `/panel` и `web_app`-кнопка **только в чате админа**. На старте бота `setChatMenuButton` для этого chat id, URL из `WEBAPP_PUBLIC_URL`. Сервер: HMAC `initData` → user id == админ, иначе 403.

Стек UI: статика из того же Go-бинарника (без отдельного Node-сервера). Пока вкладка «Сейчас» открыта — пуллинг **5–10 сек**. WebSocket не тащим. Смена состояния (зашёл / лобби / вылетел / парсер упал) дублируется пушем в ТГ админу.

### Вкладки

**Сейчас**

- какие TG-аккаунты из вайтлиста «в боте» (профиль есть, не выключен)
- кто реально сидит в BBB: в комнате / лобби / нет
- на какой паре бот сейчас (предмет, препод, слот, ссылка)
- какая пара следующая
- короткий статус записи (пишется / нет)

**Люди**

- карточка каждого: telegram id, username, имя/фамилия из ТГ, ФИО для BBB, подгруппа, вкл/выкл
- как записан кент: ФИО, подгруппа, вейкворды (править с панели)
- оригинальные вейкворды: общие + персональная фамилия и что человек дописал
- управление кентом: выключить навсегда / на сегодня, сменить ФИО и подгруппу

**Пары**

- сетка: online vs очно, подгруппа
- сохранённые ссылки BBB (ключ дисциплина+препод → URL), можно вставить/поменять
- какие лекции уже лежат в `recordings/` (имя файла, слот, размер)

**Парсер**

- последний прогон: время, ок/403/пусто, сколько пар, сколько online
- дифф, если сетка изменилась
- кнопка **обновить расписание прямо сейчас** (не ждать 7/15/19/22)

**Логи**

- лента событий с VDS: join, leave, лобби, репарс, вейкворд, «нет ссылки BBB»
- кто, какая пара, сырой текст ошибки
- хвост в sqlite (последние N), не Grafana

### HTTPS без своего домена

Telegram Mini App **не умеет** голый `http://ip:port`. Свой домен и Caddy **пока не поднимаем** — впадлу.

v1: рядом с бинарником туннель с валидным HTTPS, без DNS:

- бесплатный статический хост ngrok (`*.ngrok-free.app`) — URL не прыгает после рестарта
- или `cloudflared tunnel --url` (`*.trycloudflare.com`) — URL каждый запуск новый, тогда прописать в `.env` и перезапустить бота (он сам обновит кнопку админу)

`WEBAPP_PUBLIC_URL` в `.env`. Когда надоест ротация — купим домен, туннель останется тем же кодом.

## Ключи парсеров / STT со стороны

Кенты могут притащить API-ключи (назвали **Fish Studio**, плюс «ещё посмотрим»). Это **полная расшифровка после пары**, не стрим на лекции. Ключ в `.env`. Пока ключей нет — ogg копим, текст лекции не строим. Вейкворды от этого не зависят.

## Как это живёт

**Не монолит.** Четыре бинарника, четыре systemd-unit, одна sqlite, один `.env`. Папки `internal/*` — общая библиотека, в проде сами по себе не бегают.

```
Telegram ──► tg ──┐
                  │
rasp cron ────────┼──► sqlite (WAL)
                  │
panel (Mini App) ─┤
                  │
bbb (Chromium) ───┘
```

| Бинарник | Unit | Процесс |
| --- | --- | --- |
| `tg` | `ssau-tg.service` | Telegram: вайтлист, онбординг, T-15 Да/Нет, память ссылок BBB, кнопка Mini App админу |
| `rasp` | `ssau-rasp.service` | Парсер `ssau.ru/rasp` + cron 7/15/19/22. Кнопка в панели кладёт kick в sqlite — **этот** процесс ходит на сайт |
| `panel` | `ssau-panel.service` | HTTPS Mini App + JSON API. Единственный, кто слушает порт |
| `bbb` | `ssau-bbb.service` | Гостевой join, listen-only, лобби, рандомный выход. Chromium: отдельный процесс под запись/вейкворды + процесс под зрителей |

Связка — sqlite, не gRPC и не Kafka. `ssau.target` поднимает все четыре. Старый единый `bot` **не собираем и не деплоим**.

Chromium ставится на VDS рядом, в бинарник не бандлится. Пишет только `bbb`.

## Стек

**Go**. Четыре маленьких статичных бинарника на VDS: systemd target, `scp`, всё.

Почему не Rust: автоматизация BBB — это браузер (WebRTC, гостевая форма, «только слушать»). В Go это `rod`/`chromedp` за дни, в Rust — боль. Парсер HTML, Telegram, cron — для Go родное.

Намётки пакетов (не догма):

- Telegram: `gotgbot` или `telego`
- Расписание: `net/http` + `goquery`
- Браузер: `go-rod/rod` (удобнее живого BBB, чем сырой chromedp)
- Хранение: SQLite (`modernc.org/sqlite` или `crawshaw`) — пользователи, ссылки BBB, снимок расписания
- Звук: ffmpeg с одной вкладки. Параллельно крошечный keyword spotting (Vosk grammar / аналог) по тому же потоку: десятки–пара сотен МБ, не гигабайт.
- Полная расшифровка: **после** файла, внешнее API. Большой Whisper на VDS во время пары не ставим.

Конфиг: `.env`. В git не попадает.

## Секреты и ключи

В git не класть. Живут в `.env` на машине разработки и на VDS.

**Чтобы бот и Mini App вообще завелись — одно:**

| Что | Зачем | Откуда |
| --- | --- | --- |
| `TELEGRAM_BOT_TOKEN` | Писать/читать сообщения, кнопки Да/Нет, валидировать `initData` вебаппа (HMAC). Отдельного «ключа Mini App» нет | [@BotFather](https://t.me/BotFather) → `/newbot` → токен вида `123456:AAH...` |

Это **Bot API**, не userbot. `api_id` / `api_hash` с my.telegram.org **не нужны**. Айдишники кентов — не секреты, они уже в вайтлисте.

В BotFather ещё руками (не ключи): выключить группу/инлайн если не надо; URL Mini App можно не прописывать глобально — бот сам ставит кнопку админу через `setChatMenuButton`.

**Потом, не блокер старта:**

| Что | Когда |
| --- | --- |
| `WEBAPP_PUBLIC_URL` | Не секрет. HTTPS-адрес туннеля, чтобы открылась панель |
| `NGROK_AUTHTOKEN` | Если берём ngrok, а не cloudflared quick tunnel. Бесплатный аккаунт ngrok |
| Модели/ключи LLM для конспектов | Когда начнём собирать конспект |
| Fish Studio / прочие ключи от кентов | Расшифровка **после** записи. На паре не вызываем |
| Логин/пароль ЛК и Moodle | Пользователь вводит сам в веб-приложении; хранится зашифрованным в `accounts`, ключ — `SECRET_KEY` или `SECRET_KEY_FILE` |

Локально и на VDS один и тот же `.env`. Для разработки достаточно токена бота: парсер rasp ходит на публичную страницу без ключей.

## Данные

**Пользователь:** telegram id, строка ФИО для BBB, подгруппа, включён ли, вейкворды.

**Группа:** url/id расписания, последний сырой снимок, последний распарсенный список пар.

**Пара:** день, слот (08:00–09:35 и т.д.), дисциплина, препод, место (`online` / аудитория), подгруппа, тип.

**Ссылка BBB:** ключ ≈ `groupId + дисциплина + препод` (комната Greenlight обычно живёт семестр). Значение — URL. Если ключ пустой в момент T-15 — спросить ссылку в личке, без неё не заходить.

**Запись:** `recordings/{date}_{time}_{discipline}.ogg` плюс мета (кто из пользователей «присутствовал»).

**Событие (логи панели):** время, тип, telegram id, id пары, сообщение. Хвост для вкладки «Логи».

## Онбординг в Telegram

1. Пишет человек. Id нет в вайтлисте и это не админ → **молчание**.
2. Id в списке, профиля ещё нет → бот коротко говорит, зачем он.
3. Ссылка расписания: `groupId` берётся из env `GROUP_ID` (дефолт `531023229`), в панели только показывается.
4. «Как тебя записать в BBB?» — строка как в журнале. Фамилия для вейкворда = первое слово.
5. Подгруппа, дефолт `1`.
6. Дальше лички только этому id: T-15, вейкворды, «кинь ссылку BBB».

Админ после `/start` ещё получает кнопку Mini App (`/panel`). Настройки кентов (ФИО, подгруппа, вейкворды, вкл/выкл) — из панели, не через онбординг.

## Парсер `ssau.ru/rasp`

Публичная страница. Онлайн = `.schedule__place` содержит `online`. Препод — ссылка `/rasp?staffId=`. Подгруппа — текст `Подгруппы: N`. Слоты из колонки времени.

Рефреш в 7 / 15 / 19 / 22. Если сетка изменилась — перезаписать пары, пересчитать таймеры. Очные пары игнор, кроме того что они не должны порождать join.

Сайт иногда отдаёт 403 без нормального UA/cookie — парсеру нужен браузерный UA и, если понадобится, cookie с первой загрузки `/rasp` (как у чужих ssau-парсеров).

## Заход в BBB

На каждую включённую онлайн-пару и каждого кента с подходящей подгруппой:

1. T-15: карточка в ТГ (предмет, препод, время, Да/Нет).
2. Если ссылки комнаты нет — в той же карточке/следом: «кинь ссылку на подключение». Запомнить. Если так и не кинули — не заходим, написать об этом.
3. Молчание / Да → Chromium `--headless=new`. У каждой вкладки своё ФИО.
4. Одна вкладка — listen-only, с неё запись и споттер. Остальные — тоже listen-only, но в отдельном процессе с `--mute-audio` и фейковым микрофоном: чтобы их звук не попадал в общий null-sink и не дублировал запись.
5. Если зависли в waiting room — алерт.
6. Выйти в случайный момент из интервала `[конец_слота - 5 мин, конец_слота]`.

Две группы вкладок = **два** процесса Chrome (запись изолирована от зрителей), а не процесс на человека и не один общий на всех: один общий смешал бы звук зрителей в запись.

## Вейкворды

Это не расшифровка. Споттер слушает короткий список и орёт в ТГ сразу:

- всем на этой паре: `тест`, `контрольная`, `мудл` (`moodle`)
- лично: фамилия из ФИО, как записали в BBB

Один поток на комнату, не пять моделей. На 4 ГБ это мелочь рядом с Chrome. Полный текст лекции споттер не строит.

После выхода: ogg → API (Fish и т.п.) → конспект/поиск.

## VDS

- Linux, Chromium, ffmpeg, **четыре** бинарника под `ssau.target`. Без Docker и без nginx: `panel` сам отдаёт Mini App, TLS даёт туннель. Chromium+ffmpeg ставит `deploy/remote.sh` через apt, если их ещё нет.
- Выкат: пуш в `main` → GitHub Actions гоняет тесты, собирает `tg` `rasp` `panel` `bbb` linux/amd64 и по SSH кладёт `/opt/ssau-bot/` + юниты. `.env` на сервере руками, общий на всех, в деплой не входит.
- **1 CPU / 1 ГБ хватит** на бота + парсер + sqlite + панель (этапы 1–4).
- На заход: **4 CPU / 4 ГБ RAM + 4 ГБ swap**. Два процесса Chrome: один пишет и слушает вейкворды, второй держит зрителей (muted). Whisper на паре нет.
- 8 ГБ RAM — только если на живой паре всё равно OOM, не как старт.
- Диск под `recordings/`. Ротация не в v1, следить руками.
- Исходящие: Telegram API, `ssau.ru`, `bbb.ssau.ru`.
- Входящий HTTPS для Mini App через туннель (ngrok / cloudflared), **без своего домена** в v1. Telegram всё равно требует валидный TLS — туннель его даёт.

## Риски (не прикидываемся, что их нет)

Посещаемость гостем с чужим/своим ФИО и запись пары — серая зона правил универа и BBB. Инструмент заточен под конкретную группу. Конспекты выгружаются в **публичный** `r4r1ty-tech/LectionsSSAU` — он специально открыт для своей группы, туда писать только учебные материалы, без персональных данных. Не светить токены и записи.

Технически хрупко: смена вёрстки rasp, новая ссылка комнаты, модератор не пускает из лобби, BBB обновляет клиент.

## ЛК и Moodle

Синк живёт в процессе `rasp` (`internal/uni`): расписание из ЛК каждый час днём, Moodle раз в 30 минут (полный обход курсов раз в 6 часов и сразу после подключения). Подключение — «Ещё → Аккаунт универа» в веб-приложении (тот же логин пробуется и в ЛК). Тесты на посещаемость бот не решает и не отслеживает.

Дальше по конспектам: распознавать текст и содержание слайдов и собирать конспект по слайдам вместе с расшифровкой.

### ИИ-решение тестов Moodle

Сделать взаимодействие с тестами Moodle так, чтобы ИИ мог проходить квизы с опорой на материалы лекций (конспекты, расшифровки, слайды):

- **Изучение Moodle:** разобрать живую структуру квизов (`mod/quiz/*`: старт/продолжение попытки, `attempt.php`, `processattempt.php`, `sesskey`, типы вопросов — один/несколько вариантов, соответствие, ввод текста, навигация по страницам, таймер и лимит попыток).
- **Доступ к лекциям:** передавать модели релевантный контекст по предмету (готовые конспекты `notes`, `transcript.txt`, тексты слайдов).
- **Прохождение:** чтение вопроса и вариантов ответа → выбор ответа LLM → выставление ответа в форме Moodle (режим и уровень автономности — подтверждение или автоотправка — уточнить после разбора живых тестов).

## BBB без браузера (реализовано)

Chromium (две группы вкладок, PulseAudio `ssau_rec`) полностью заменён в `bbb` и `capture` на прямой Go-клиент (`internal/bbb` + `internal/capture/opus.go`). Chromium на VDS нужен только для разовой печати PDF конспектов (`internal/notes/pdf.go`).

Снятый и проверенный вживую на `bbb.ssau.ru` (Greenlight `release-2.14.8.1` → BBB `2.6.18`, `bbb316.ssau.ru`) протокол:

1. **Вход гостем через Greenlight (`HTTP`):** `GET` формы → `csrf-token` + поле `[join_name]` → `POST` с редиректом на `sessionToken` (или на `guestWait` при включённом лобби, где опрашивается `/bigbluebutton/api/enter`).
2. **Параметры и STUN/TURN:** `/bigbluebutton/api/enter?sessionToken=…` (`meetingID`, `internalUserID`, `authToken`, `externUserID`, `guestStatus`) и `/bigbluebutton/api/stuns?sessionToken=…`.
3. **Присутствие и чат (`SockJS` + Meteor `DDP`):** `wss://<host>/html5client/sockjs/.../websocket` → `validateAuthToken` (`validationStatus: 3`), `ping`/`pong`, подписки (`users`, `meetings`, `group-chat`, `group-chat-msg`, `voiceUsers`, `presentations`, `slides`), `sendGroupChatMsg` (в BBB `2.6.18` обязательны `chatEmphasizedText: false` и `sender: {id, name, role}`), выход — `userLeftMeeting`.
4. **Звук listen-only (`bbb-webrtc-sfu` + `pion/webrtc/v4`):** `wss://<host>/bbb-webrtc-sfu?sessionToken=…` (`listenOnlyOffering: false`) → `start` (`role: "recv"`, `type: "audio"`) → `startResponse` (offer сервера) → `subscriberAnswer` (`sdpOffer`) → `webRTCAudioSuccess` (`MEDIA_FLOWING`). RTP `audio/opus` (48 кГц stereo) пишется напрямую в `.ogg` без перекодирования и параллельно декодируется через `ffmpeg` в 16 кГц PCM для вейквордов Vosk (`internal/capture/opus.go`).
5. **Слайды:** подписка DDP на `presentations` и `slides` + прямая загрузка PNG/SVG по HTTP (SVG растеризуется через `ffmpeg`/`rsvg-convert`/`magick`).

Живая проверка на тестовой комнате `https://bbb.ssau.ru/b/202-jzg-jbj-n68`: бот зашёл без браузера, корректно отразился в комнате, отправил и прочитал сообщения в общем чате, принял WebRTC-поток и записал реальную речь в `.ogg` (**21.02 с**, **193 377 байт**, **1051** RTP-пакет `audio/opus`, `mean_volume: -23.6 dB`, `max_volume: -3.9 dB`, кодовая фраза `"кодовая фраза галочка"` прослушана и подтверждена). Риск хрупкости остаётся только при мажорном обновлении BBB (например, переезд на 3.0 с GraphQL вместо DDP).

## Сверка с кодом (13.11.2026)

Разделы выше местами описывают замысел, а не то, что в коде. Где расходится — прав код (и docs/ARCHITECTURE.md, он в основном актуален). Основное:

**Расписание и данные**
- Рефреш: 07/15/19/22, а при загруженном ключе шифрования ещё и **каждый час 07–21** (даже без аккаунта ЛК — тогда ежечасно публичный сайт).
- Группа: работает только `GROUP_ID`; `GROUP_CODE` лишь показывается в панели. Если группы из конфига нет в ЛК, синк молча берёт первую группу студента.
- Ключ комнаты BBB: `room|предмет|препод|тип` (+ `lesson:<id>` у конкретной пары, + ссылка из ЛК); `groupId|предмет|препод` — самый низкий приоритет, пишет только панель.
- Записи: `recordings/<предмет>/лекция-N/audio.ogg`, не `{date}_{time}_…`. Сырой снимок расписания не хранится — только `parse_runs` (статус, счётчики, дифф).
- Подгруппа пары `0` = вся группа; API принимает 1–4, интерфейс предлагает 1–2.

**Заход в BBB (обновлено после переезда без Chromium)**
- **Прокси есть**: SOCKS5-пул из `PROXY_FILE` (дефолт `/opt/ssau-bot/proxies.txt`), каждая сессия — свой прокси для HTTP и WebSocket; файла нет — напрямую.
- Сессии присутствия и пишущая сессия работают в одном Go-процессе `bbb` (`DirectJoiner`: Greenlight HTTP + Meteor DDP + Pion WebRTC) без запуска Chromium и без PulseAudio. Лимита на число зрителей нет.
- Выход 0–5 минут до конца — только у зрителей; пишущая сессия выходит ровно в конец пары.
- Молчание на T-15 = заход за **5** минут до пары; «Зайти за меня» — за 15. Кнопки «Зайти за меня / Не сегодня», не «Да / Нет».
- Зрители аудио-поток не поднимают (только DDP-присутствие); listen-only через `bbb-webrtc-sfu` + `pion/webrtc/v4` поднимает только пишущая/listen-сессия.
- **Бот пишет «Здравствуйте» в общий чат BBB** при каждом заходе — вопреки «ответы в чат не делаем». Решить: оставить или убрать.
- Вейкворды: Vosk распознаёт всю речь без грамматики (с грамматикой ловил ложные «тест»), слова ищутся в Go. Текст в файл не пишется.
- `LECTURE_PAUSE=1` (дефолт): на время пары SIGSTOP процессам `cursor-agent`/`cursor-server` на VDS и удаление `/tmp/cursor-sandbox-cache`.
- После пары сбор слайдов идёт по DDP + HTTP (до 60 слайдов), а Chromium (`CHROME_BIN`) нужен только на этапе сборки `notes.pdf` (`print-to-pdf`).

**После пары**
- STT: AssemblyAI → Fish → Groq Whisper. Vision слайдов: Groq (qwen) → Grok. LLM: любой OpenAI-совместимый `chat/completions`, `LLM_MODEL` обязателен. PDF: goldmark + KaTeX + `chromium --headless --print-to-pdf`.
- Распознавание текста слайдов уже есть (VLM, не OCR) — этап 12 сделан частично, нужен по качеству.
- В публичный `LectionsSSAU` уходят `transcript.txt` (вся речь пары) и `notes.pdf`. После публикации `audio.ogg` удаляется сразу, остальное через 24 ч — локального архива не остаётся.
- Ключи `ASSEMBLYAI/FISH/GROQ/GROK` деплой не ставит — только руками в `.env` на VDS. Без `GITHUB_TOKEN` публикация молча выключена.

**Панель и бот**
- Экраны «Сегодня / Неделя / Сдать / Конспекты / Ещё»; пульт (Тест, Сейчас, Люди, Парсер, Логи) — в «Ещё → Служебное», опрос раз в 4 с.
- Вход в панель — пароль `PANEL_PASSWORD` или список `PANEL_ALLOW_IPS`; **проверки Telegram initData нет**, «только админ» на сервере не проверяется — любой с паролем видит весь `/api`. `PANEL_DEMO=1` обходит пароль.
- HTTPS: только cloudflared quick tunnel (`deploy/tunnel.sh` сам переписывает URL, бот подхватывает за 20 с). ngrok и Caddy в деплое нет. `LISTEN_ADDR=:8080` слушает все интерфейсы по http; за туннелем фильтр по IP видит только loopback без `PANEL_TRUST_PROXY=1`.
- Аккаунт универа подключается и в панели, и в боте (`/connect`, пароль удаляется из чата). В боте ещё `/tasks`, кнопка «Сдать», напоминания за 24 и 3 ч. Тексты бота местами говорят про «три кнопки».
- Онбординг в Telegram: ФИО → подгруппа → вейкворды (с «Пропустить»). Правила ФИО разные: бот 2–4 слова до 80 символов, панель от 2 слов, API до 64.
- `ssau.target` поднимает пять юнитов (четыре процесса + туннель).

## Известные баги (из сверки)

1. Пак только из слайдов (речи нет) не публикуется: `Transcript` указывает на несуществующий `transcript.txt`, публикация падает и повторяется каждые 5 минут без лимита.
2. Пустая запись при наличии слайдов всё равно уходит в vision и LLM и рассылается как готовый конспект (доки обещают обратное).
3. Слайды с 41-го по 60-й молча отбрасываются перед vision.
4. Неудачный сбор слайдов не повторяется (`slides_done` ставится всегда).
5. Повтор конспекта заново платит за STT и vision — готовый `transcript.txt` не используется как кэш.
